`v0.2.2` is tagged on main `5b8c82e` and pushed. Part 1's suite is still 373 tests. Part 2's is 923: the 8 new ones test section 13's check by name, which my last mail said the suite didn't test yet.

**The new key `writes`.** It goes with `bind`: for a bound name, what its code writes for each value typed through it. A string is a scalar's text, written as spelled, and a mapping is written as a mapping. A bound name without `writes` writes back what it was given, as before. `suite-to-data` writes it to `writes.json`, as JSON (`{"signed": "+5"}`), and the tests are tagged `writes`.

**The 8 tests** come in pairs, with `signed: !int(/[-+][0-9]+/)` or `point` bound. In each pair, code writing the first is written, and code writing the second has `emit: refused`:

1. `ZGD5` and `XY9M`: `!signed` on `+5`, the code writing `+5` or `5`. `5` doesn't match the pattern, so reading it back refuses the document.
2. `K8MQ` and `7QQG`: `{!|: [!signed, !str]}`, the same. `5` reads back as the string `"5"`, with no error.
3. `6XE6` and `9UJP`: `{!|: [!small, !signed]}`, with `small: !int(0..9)`, the same. `5` reads back as the int 5 through `small`. The typed events are the test's own, so a harness comparing typed events alone passes `9UJP`. Only the name tells it apart.
4. `J849` and `4EC4`: `{!|: [!point, !sweep]}` on `x: 1` and `y: 2`, the code writing `{x: 1, y: 2}` or `{target: 3}`. The second reads back as a sweep.

Read back with the test's `bind`, each written test gives its `calls` again, and each refused one that reads back gives other calls. So a harness can check the name by comparing `calls` too.
