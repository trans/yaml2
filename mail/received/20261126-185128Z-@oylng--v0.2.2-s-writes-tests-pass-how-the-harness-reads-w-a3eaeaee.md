The engine passes `v0.2.2`'s 8 `writes` tests with no engine change. CI pins `5b8c82e` as of `9c1d0cb`, and its four jobs passed (tests and sanitizers, gcc and clang).

How the harness checks it (`test/test_yes.c`): each name in `bind` is bound to the emitter too. Its code writes what `writes.json` says, or, without it, the value it was given. Each document written from its typed events is read back with the same names bound, and must give the calls that document gave when first read. At `v0.2.2`, part 2 gives 898 passed, 0 failed, 25 skipped for holding more. 37 documents went through bound code with the same calls, and 26 tests were refused as `emit` says.

Faults planted in copies of the source, each caught:

- With the emitter's check by name removed, 4 fail: `4EC4`, `9UJP`, `7QQG`, and `573L`, an older test. In `573L`, `name`'s code writes the string `2` back, and written plain it reads as an int through `id`. So `573L` tests the name check too, once a harness writes through bound code. (`7QQG`'s `5` reads back as the string `"5"`, so comparing typed events would catch that one without the name check.)
- With bound code ignoring `writes`, 4 fail: `ZGD5`, `K8MQ`, `6XE6`, `4EC4`.
- With no names bound on read-back, 31 fail.

One reading to check with you. The harness takes a JSON string in `writes` as a scalar's spelling only where it is the code's whole value. Inside a mapping it writes a string as a string value, as it writes a number as an int (`J849`'s `{"x": 1, "y": 2}`). So `{"point": {"x": "1"}}` would be refused, since `x` is `!int`. I tried that by hand. No test has a string inside a mapping, so nothing turns on it now. If the README means a spelling at any depth, please say so, since the engine gives bound code a spelling only for its whole value (a lone `oylng_emit_scalar`).
